# API 契約設計

## 目的與邊界

將需求、Controller／DTO、現有規格或經去識別化的請求回應，整理成提供端與呼叫端可共同確認的介接契約。使用繁體中文，保留 method、path、欄位與技術名稱原文。

沿用本專案工作 skills 的手動指定政策。只處理本次指定的 endpoint 或介接範圍；既有 API 的契約整理、契約變更提案與新 API 設計都可使用。

- 單純追查 API 錯誤屬於除錯；ETL 批次、重跑與資料寫回流程屬於資料流程設計。
- 契約設計不代表要求修改服務實作、執行遠端請求或部署。若使用者另有要求，依其指定範圍處理。
- 延續既有 route、認證、命名及回應格式；改善建議另列為提案，不把新格式描述成現況。

## 工作方式

1. 確認提供端、呼叫端、介接目的，以及要描述現況或提出變更。查看相關 route、Controller、DTO、驗證規則、認證設定、既有規格與測試；只讀取和目標介面有關的內容。
2. 將資訊分為「已確認現況」、「設計提案」、「待確認」。記錄來源檔案或規格版本；程式碼與文件不一致時列出差異，不能默默選一方。沒有來源時可以提出草案，但不可聲稱已實作或已驗證。
3. 定義 endpoint 的 method、path、認證與授權範圍、輸入、成功及錯誤回應。使用 [契約模板](references/contract-template.md) 整理完整規格；單一欄位或狀態碼修訂只輸出相關部分。
4. 對每個欄位分別說明必填、允許 null、缺省值、限制與業務語意。區分未提供、null、空字串和空陣列；部分更新尤其要說明「不修改」、「清空」與「不接受」的條件。未確認的規則不能自行補成既定事實。
5. 依介面需求補充分頁與排序、時間與時區、識別碼格式、重試與重複請求行為。寫入逾時不代表伺服器未寫入；冪等鍵、重複判定或狀態查詢若尚未實作，須列為提案或缺口。
6. 比較變更前後對既有呼叫端的影響，列出相容性風險、過渡方案與待決事項。需要 JSON 範例或邊界判斷時，讀取 [範例與檢查情境](references/contract-examples.md)。

## 契約判斷原則

- 描述錯誤時同時記錄 HTTP status、response body 與呼叫端行為；若既有服務以 HTTP 200 搭配 body error，保留並說明此現況，不套用自行設計的格式。
- 認證與授權分開說明：身分如何識別、誰可執行此動作、是否有資料列或租戶範圍限制。範例使用合成資料與 placeholder，不填入真實 token、密碼或個資。
- 分頁要交代參數、預設值與上限、排序穩定性、結束條件，以及資料異動時的預期行為。total count 或 cursor 只有在契約確實提供時才列入。
- 對 ArcGIS REST 介接，先確認既有服務 metadata／文件中的欄位、能力與限制；說明 geometry、spatialReference 及結果截斷的判讀。不得把自有 API 的 envelope 或能力假設套到既有 ArcGIS 服務。
- 新增 response 欄位、enum 值或更嚴格的驗證，都要根據既有呼叫端行為評估相容性；不能一律視為安全變更。
- 使用者要求 OpenAPI 時沿用指定或現有的 OpenAPI 版本，讓 schema、範例與文字規則一致。使用專案現有工具驗證；沒有執行工具時明確標示未驗證，不宣稱規格通過驗證。

## 輸出與驗收

完整契約至少讓接手者找得到：介面目的與版本、endpoint 清單、欄位規格、成功與錯誤回應、相關認證及分頁規則、範例、相容性影響、假設與待確認事項。依規模省略不適用章節，避免為小幅修訂輸出整份模板。

交付前檢查欄位名稱、型別、必填／null 規則、狀態碼與範例是否一致；錯誤案例是否涵蓋本次需求的重要分支；是否把實際執行過的驗證和建議驗證分開記錄。

## 交接資訊

依本專案慣例附上精簡摘要，不自動啟動其他 skill：

- 目前階段：草案、待介接雙方確認或已確認。
- 已完成／已確認：本次 endpoint、欄位及錯誤規則。
- 尚未確認／待決：業務語意、權限、限制或相容性決策。
- 重要假設：資料來源、版本、時間及呼叫端前提。
- 主要風險：破壞性變更、重複寫入、資料曝露或分頁遺漏。
- 建議下一步：契約確認、實作或契約測試。
- 相關產物：來源檔案、規格、範例與實際驗證紀錄。
